# ADR-006

Status: Accepted
Data: 2026-07-27

## Contexto
O projeto SmartMonitor API vinha acumulando dívida técnica em várias frentes:
1. Um grande arquivo monolítico `views_deprecated.py` contendo código obsoleto (endpoints v1 descontinuados) misturado a fluxos ainda ativos (`ClassificacaoPH`).
2. Conversores intermediários entre as chamadas ao banco relacional e as rotinas de Machine Learning induziam *round-trips* ineficientes (`pd.DataFrame` -> `dict` com chaves em string -> reconversão para `pd.DataFrame`).
3. Uso intensivo de herança complexa via uma classe abstrata `Tratamento`, acoplando comportamentos ortogonais e poluindo serviços.
4. Pastas profundamente aninhadas sob `ml_pipeline` sem separação coesa entre controladores da API, adaptadores e regras de negócio puras.

## Decisão
Adotar **Arquitetura Modular** em 4 camadas modernas sob `appSM` e refatorar o pipeline em memória:
1. **Separação por Camadas Coesas:** Criados os diretórios `api/` (Endpoints e Serializers), `services/` (Casos de Uso), `domain/` (Modelagem matemática e Limpeza de Dados) e `infrastructure/` (Acessos SQL externos com *Module-level Lazy Engine*).
2. **Composição sobre Herança no ML:** Substituída a classe abstrata de `Tratamento` por um módulo puro de domínio (`appSM/domain/tratamento.py`) fornecendo a função sem estado `normalizar_historico(data)`.
3. **Fluxo End-to-End em DataFrames:** Eliminação completa da chamada legada `dataframe_para_historico`. Os consultores de banco entregam estruturas nativas do Pandas sem perdas temporais, as quais passam intactas pelo pré-processador e pelas engines de ML/Estatística.
4. **Purgação do Legado:** Exclusão de `views_deprecated.py` com o redirecionamento dos endpoints essenciais diretamente na camadade apresentação V2 (`api/views.py`).
5. **Characterization Tests:** Implementados testes de caracterização blindando as fórmulas matemáticas para impedir qualquer desvio acidental de precisão.

## Alternativas Consideradas
- Mantê-lo num formato modular aninhado dentro de `ml_pipeline/`, porém falhava em sanar os overheads em memória (round-trips) e separações entre Presentation e Infrastructure.
- Uso do padrão *Singleton class-level* em vez de *Module-level Lazy Engine* no `db_fetcher.py`; entretanto, a engine a nível de módulo entregava sintaxe mais idiomática no Python sem boilerplate.

## Consequências Positivas
- Código significativamente mais conciso, com exclusão imediata de quase mil linhas de código morto ou obsoleto.
- Economia computacional por redução drástica de parsing repetitivo de strings temporais em memória.
- Navegação de arquivos autoexplicativa e compatível com as melhores convenções de desenvolvimento orientado a domínio no Django/Python.
- Manutenção integral do histórico do Git mediante comandos mapeados a renomeações.

## Consequências Negativas
- Pequenos aumentos no número de imports inter-módulos dentro dos pacotes do `appSM`, esperado nas transições para camadas divididas.
- A exclusão deliberada e definitiva do contrato de roteamento da v1 rompe integrações arcaicas, requerindo que os clientes homologados chamem pontualmente as rotas autênticas de `/v2/*` ou `/classify/ph`.

## Impacto Técnico
- Todos os testes relocalizados para importações centralizadas em `appSM.api.*`, `appSM.services.*`, `appSM.domain.*` e `appSM.infrastructure.*`.
- Configurações de logging e parâmetros de persistência remapeadas limpas em `settings.py` (com logger renomeado para `appSM.services` e apontador para modelos sob o domínio).

## Quando Revisar
Se novos requisitos não relacionais, transições para banco vetorial de IA ou alteração nos backends analíticos imporem uma arquitetura assíncrona orientada a eventos, exigindo abstração adicional de repositórios.
